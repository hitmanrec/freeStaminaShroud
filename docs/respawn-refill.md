# 0.6.0: полные здоровье, стамина и мана после возрождения

Добавлено однократное восстановление текущих значений Health, Stamina и Mana
до текущих максимумов этого персонажа после подтверждённой смерти и оживления.
Реализация экспериментальная: native проверки пройдены, игровая проверка
ещё нужна. Существующие правила спринта, прыжков и инструментов сохранены.

## Срабатывание

1. Сервер сообщает PLAYER_DIED. Дополнительный путь — EntityDiedEvent,
   если API однозначно сопоставляет умершую сущность с подключённым игроком.
   Оба пути используют одну запись ожидания; NPC не ставят пополнение игрока.
2. Ожидание привязано к ключу аккаунта внутри процесса, а не к номеру слота
   или старому entity ID. Ключ аккаунта в лог не выводится. Замена сущности
   при возрождении не теряет запись.
3. Игра сама оживляет персонажа: Health должен стать положительным, а активный
   Actor.currentColliderMode — перестать быть Death (5) / DivingDeath (9). Пока это не выполнено, мод ничего
   не пополняет. Ожидание в меню смерти может длиться долго.
4. Все три атрибута должны быть доступны, максимумы — одинаковыми на двух
   последовательных опросах. Обычно это 250–500 мс после готовности персонажа;
   при изменении характеристик проверка начинается заново.
5. Получаются все три writable-компонента через официальный component_write.
   Их контейнеры и максимумы перепроверяются до любой записи. Только после
   успешной проверки всем трём текущим значениям присваиваются максимумы.
6. Ожидание удаляется сразу после одного пополнения. Последующий урон и
   расходы ресурсов работают обычно. Не создаётся окно постоянного лечения.

PLAYER_LEFT отменяет ожидание, смена мира очищает весь кэш. Обычный вход,
переподключение, телепортация и изменение maximum без события смерти не дают
пополнения. Если после появления живого персонажа API/характеристики не
позволили выполнить запись за 10 секунд, ожидание отменяется с диагностикой.
Это исключает слишком позднее лечение после нерешённой ошибки записи.

PLAYER_DIED имеет ограничение самого загрузчика: он не фиксирует некоторые
смерти, например от замерзания/администратора. Для них может помочь EntityDiedEvent,
если игра его подняла и player API ещё узнаёт сущность. Если не пришло ни одного
подтверждения, мод не угадывает смерть по входу в мир или одной смене entity ID.
Поднятие союзником сработает, если до него зарегистрирована такая смерть;
отдельный сценарий подъёма без события смерти пока не обещается.

## Почему однократная запись

Максимумы читаются после возрождения, с действующими на этот момент эффектами,
вместо фиксированного числа 10000. Не нужно создавать регенерационный бафф,
обходить задержки регенерации или сохранять высокую регенерацию на секунду,
когда персонаж уже может получить новый урон. В компонентной записи загрузчик
сам отмечает изменение, чтобы игра обработала репликацию и сохранение.
Network*/Client* копии не редактируются.

Метаданные контейнеров, maximum slots и корневые атрибуты берутся из API
поддержанной сборки. Проверяются размеры, корневой ID, initialized flag,
storage offset/count, диапазон индекса максимума и неотрицательный maximum.
Нет сырых записей через указатели из read-only component или изменения
постоянных максимумов, регенерации, инвентаря и длительности еды.

## Обновление и короткий тест

Закрыть игру, выполнить `git pull --ff-only`, `sh scripts/build-probe.sh`,
переустановить через `scripts/install-probe.py --game-dir … --replace`.
В логе должно быть `probe=0.6.0` и `respawn_guard status=0`.
При ошибке guard сохранить оба свежих лога, не обходить проверки.

Первый тест можно сделать одному:

1. Войти с неполными ресурсами, постоять: само подключение не должно дать
   мгновенного пополнения от мода (штатная регенерация продолжает работать).
2. Потратить ману/стамину, погибнуть от врага или падения и возродиться.
   После готовности персонажа все три полосы должны дойти до текущих максимумов.
3. Сразу затем потратить ресурс или получить урон: мод не должен снова его
   пополнять до следующей смерти. Штатную регенерацию учитывать отдельно.
4. Повторить смерть ещё раз, чтобы проверить повторное взведение.

Сохранить оба лога и результат. Затем можно повторить гостем без установки
мода у него; остальные игроки должны оставаться со своими значениями.
Работа предыдущих функций на госте проверена, новая функция возрождения
на госте пока не подтверждена.

## Лог

- `respawn_guard status=0`: API, схемы и подписки доступны.
- `respawn_death entity=… cause=…`: поставлено ожидание; cause 4294967295
  обозначает дополнительный путь EntityDiedEvent без определения причины.
- `respawn_wait … reason=dead_health/actor_not_alive/resources_unavailable/character_missing`:
  причина ожидания, не чаще heartbeat.
- `respawn_write status=…`: не прошёл preflight writable-компонентов.
- `respawn_refill slot=… entity=… health=старое->максимум stamina=… mana=…`:
  выполненная однократная запись.
- `respawn_cancel_left`: ожидание удалено при выходе.
- `respawn_expired`: окно записи после готовности живого персонажа истекло.

Native fake-host тесты покрывают вход без лечения, ожидание мёртвого персонажа,
Death/DivingDeath modes, долгую паузу в меню смерти, три одновременных ресурса, отсутствие
повторного лечения, разные максимумы/игроков, смену entity/slot у гостя,
нулевой максимум маны, ошибки preflight без частичных записей, изменение
максимума после оживления, отключение, повреждённый контейнер и неизвестную
сборку. Дополнительно выполняется ASan/UBSan и сборка Windows DLL.
