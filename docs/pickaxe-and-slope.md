# 0.5.2: подтверждённая кирка и отдельная диагностика склона

Пользователь уточнил, что в сессии 0.5.1 на горе и при добыче киркой расход
сохранился. Наблюдавшиеся 25 обнулённых прыжков не означают, что подавлены
все способы расхода при подъёме, включая возможный непрерывный накопитель
или клиентское предсказание.

## Кирка

В `19-45-10` повторяющиеся mining HitEvent (`hasMiningVolume=1`, weapon PIDE
8141) совпадают с 17 стоимостями -3 текущего item ID **2671192505**. Это
стабильный ID ресурса предмета из SlotSelection, не session PIDE.
В предыдущем логе 0.5.0 этот item ID также сопровождался серией добычи.
При анимации 04 текущий классификатор всё равно выдавал reason 6.

В 0.5.2 добавлено явное распознавание этого подтверждённого item ID на
проверенных сборках. Первое и последующие действия этой киркой подавляются
по её текущему предмету и проверенному месту списания, без ожидания попадания,
независимо от цели/боя/текущей анимации. Определение не обучается по истории
попаданий и не использует PIDEs текущей сессии.

Общее правило Tools + TwoHanded для остальных инструментов сохранено.
Другие варианты кирок с другими item ID отдельно не подтверждены: если они
не подходят под общее правило, потребуется проверка их классификации.
Обычное двуручное оружие целиком бесплатным не становится.

## Более точные причины отказа инструмента

Раньше reason 6 объединял несколько причин. Теперь дополнительно:

| action_reason | Смысл |
| --- | --- |
| 6 | Недоступна схема/компонент выбора предмета или необходимый API |
| 9 | Нет item ID или item_info не вернул предмет |
| 10 | Категория предмета не Tools и ID не распознан явно |
| 11 | Не подходит/недоступна анимация обычного правила Tools |

action_detail сохраняет item ID. Эти сведения позволяют разбирать другие
кирки без предположения, что любое двуручное оружие — инструмент.

## Склон: измерение источника, не объявленное исправление

Статическая система `stamina_depletion_climb_wall` на RVA `0x2f0600` добавляет
float-расход в накопитель на `0x2f09f6` и сохраняет его на `0x2f09fa`.
Она может оказаться источником расхода на крутом подъёме, но связь с этим
сценарием пока не доказана. Обычное лазание отключать без такого подтверждения
не следует; новая версия эту стоимость не подавляет.

Добавлены два read-only hook_at: перед ADDSS (`0x2f09f6`) и после MOVSS
(`0x2f09fe`). Между ними исполняются исходные инструкции игры. Они измеряют
четыре байта реального операнда RAX и только для совпавшего свежего серверного
компонента игрока. Кэш не разыменовывается; измерители не вызывают ECS,
не пишут в игровые компоненты/регистры и не меняют результаты инструкций.
Enshwick сохраняет SIMD-состояние вокруг mid-hook callback.

Guard проверяет сборку, адрес системы, .text и 18 байт
`[0x2f09f2,0x2f0a04)`, FNV-1a `0x8a76d895` в обоих проверенных отчётах.
Оба участка перехвата не перекрываются. При неполной регистрации измерение
остаётся выключенным; зарегистрированный одиночный callback ничего не меняет.

Старт: `climb_trace_hooks status=0`. Новые строки `climb_trace` содержат slot,
entity, `samples`, `changed`, `dropped`, `before_float_bits`, `after_float_bits`.
Числа bits — сырые IEEE-754 float32, не готовая величина расхода.
`changed>0` показывает изменение накопителя между этими инструкциями.
Последние before/after относятся к последней паре измерений, не обязательно
к самой большой дельте интервала. Конфликтующие измерения учитываются как dropped.

Отрицательный результат этого источника не доказывает отсутствие расхода:
могут остаться другие ветки, клиентское предсказание или несовпавший указатель.
Нужны сопоставление с серверным stamina_status и описание действия пользователя.

## Один короткий прогон

Обновить, собрать и установить 0.5.2 с `--replace` при закрытой игре.
Вне боя: 3–5 ударов той же киркой по руде/земле, 5 секунд стоять, затем
10–15 секунд повторять именно тот подъём/прыжки на горе, где расход виден.
Не использовать планер и другие действия в этом интервале, потом постоять
ещё 5 секунд и выйти. Достаточно одного игрока.

Прислать оба свежих лога и порядок действий. Если возможно, отметить момент
начала подъёма или записать короткое видео: серверный запас и видимый индикатор
могут отличаться. Ожидаем для кирки reason 1/applied_delta 0. Для горы сначала
проверяем источник, не обещаем его исправления в этой версии.

Native tests и ASan/UBSan проверяют подтверждённую кирку, отказ для соседнего
неизвестного ID, сохранение стоимости оружия и неизменность регистров/операнда
измерителями. Сама игра/Proton в облаке не запускалась.
