# Точки расхода: результат статического исследования

## Подтверждённое разделение механизмов

1. `HitEvent.staminaChange` относится к пути применения попадания, в том числе
   потере стамины при блокировании. Перехват всех таких изменений отменил бы
   часть боевых расходов и не решил бы спринт/добычу. Источник:
   [EMF combat](https://github.com/matenm/emf-enshrouded/blob/7d014b2d42cb63196fe147a389ed13dea69d1f6d/docs/engine_parts/combat.md).
2. В пользовательских логах стамина расходуется при EMPTY_SWINGS без попаданий.
   Поэтому итоговый HitEvent не может быть единственной точкой отмены стоимости
   инструмента. Требуется найти сам дебет действия или его расчёт до списания.
3. `StaminaDepletion.accumulatedValue` — промежуточный накопитель, не текущий
   запас. Изменять его глобально нельзя: путь может объединять планёр, движение
   и другие расходы. Его потребитель ещё не установлен для сборки `26320373`.
4. Доступен отдельный пример `StaminaDepletionMod_Glider` в SF Unlimited Flight,
   но это не свидетельство отдельного проверенного API для двойного прыжка,
   склона, спринта или инструмента.
5. В исследованной reflection есть `ItemScaledCostSetup.staminaMod`, а также
   общие impact-узлы `ChangeAttribute`. Модификатор предмета без различения цели
   может сделать бесплатными и атаки врагов этим предметом — такой патч не
   соответствует требованиям. Присутствие поля ещё не устанавливает его вызовы.

## Уточнение прыжков

По сведениям пользователя: обычный прыжок уже бесплатный; двойной прыжок и
прыжки вверх по склону расходуют стамину. Политика разделяет `ordinary_jump`,
`double_jump`, `slope_jump`: обычный сохраняет исходное поведение, два остальных
бесплатны только вне боя. Планёр всегда сохраняет обычную стоимость.
Это семантические категории нашей политики, не утверждение о трёх разных
функциях движка. Их соответствие игровым действиям предстоит установить.

## Почему пока нет игрового перехвата

В C ABI Enshwick, на который собран проект, есть hooks/отражение/чтение
компонентов, но готовый callback «списать X за это действие этого игрока»
в просмотренных API не найден. В доступных таблицах нет проверенного нами
контракта такого hook для EXE пользователя. Архивные адреса исследования
`1076226` не являются адресами его сборки `26320373`.

Для установления функции нужен сам бинарный код текущей EXE или статический
отчёт о нём. В облачном репозитории есть исходники модов и логи, но нет игры.
Мы не можем получить надёжную сигнатуру функции из значений стамины в логе.
В проект не добавлены угадываемые offsets, универсальное бесконечное заполнение,
отмена блокирования или возврат уже потраченной стамины.

## Одноразовый офлайн-отчёт на Arch, без игровой сессии

В репозитории есть `scripts/inspect-game.py`. Он **не запускает** EXE, не
подключается к процессу, не использует сеть и не меняет игру. Читает PE-заголовки,
CodeView fingerprint, таблицу `.pdata`, упоминания трёх известных идентификаторов
в исполняемых секциях и отбирает релевантные названия. `objdump` сохраняет
дизассемблирование найденных функций с их границ `.pdata`.

```sh
sudo pacman -S --needed python binutils
git pull --ff-only
GAME_DIR="$HOME/.local/share/Steam/steamapps/common/Enshrouded"
python3 scripts/inspect-game.py --exe "$GAME_DIR/enshrouded.exe" \
  --out .build/offline-report
tar -czf .build/offline-report.tar.gz -C .build offline-report
```

Для другой Steam-библиотеки измените `GAME_DIR`. Запускать игру или мод,
переключать фокус и проходить сценарии не нужно. Скрипт отказывается
перезаписывать непустой каталог отчёта — для повторного запуска задайте новый
`--out`. Нужны только `report.json` и `function-*.txt`, либо созданный архив;
полную EXE и `enshrouded.kfc` передавать не требуется. Отчёт можно прислать
в чат. При сохранении в Git не добавляйте EXE, всё содержимое `.build/` или
бинарники загрузчика.

В JSON нет полного пути установки или PDB-пути; только fingerprint, SHA-256,
секции, имена-кандидаты и адреса. Отчёт содержит фрагменты машинного кода игры,
а не исполняемый мод. Перед публикацией просмотрите его.

Ограничения: совпадение четырёх байт может быть частью другого операнда;
`.pdata` может не описывать leaf-функцию; имя не доказывает назначение кода.
Каждое совпадение обозначено **кандидатом**, а не проверенной точкой записи.
По умолчанию выводится до 40 функций и до 64 КиБ кода каждой; пропуски явно
отмечаются. Нулевой результат не означает отсутствие нужного механизма.

## Дальнейшая работа по отчёту

Для каждого кандидата различить чтение/сериализацию, регенерацию, инициализацию
и настоящий расход. Затем установить аргументы и владельца-игрока, отделить
планёр/блок/атаку от спринта/прыжка/добычи и только после этого связать дебет
с политикой и доказанным состоянием боя. При нехватке информации сначала
использовать более узкий статический разбор, а не повторять все игровые тесты.
