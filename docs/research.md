# Исследование интеграции Enshrouded

Дата: 2026-11-03. Проверены открытые исходники и документация; игра в облаке
не установлена. Ни совместимость с пользовательской сборкой, ни поведение
гостей не проверены в игре. Ссылки ниже закреплены за исследованными коммитами.

## Основные выводы

- Игра содержит связанные с боем компоненты и поля. Готовый достоверный
  `is_player_in_combat` для наших целей пока не найден.
- Готовые примеры бесконечной стамины не реализуют наши избирательные правила.
- Для Windows-игры под Proton существуют загрузчики. Отдельный Linux ELF-мод
  не является исходным требованием: сначала проверяем Windows DLL под Proton.
- Встроенный хост действительно выполняет серверные системы. Это позволяет
  исследовать host-only вариант, но не доказывает нужное поведение гостей.
- Предпочтительный следующий шаг — диагностический мод без изменений стамины,
  с определением точной сборки и чтением состояния отдельных игроков.

## Определение боя

В [сгенерированных типах EMF](https://github.com/matenm/emf-enshrouded/blob/7d014b2d42cb63196fe147a389ed13dea69d1f6d/sdk/include/emf/generated/components.hpp)
найдены:

- `keen::ecs::CombatStance`: `combatStanceDuration`, `combatStanceEndTime`.
- `keen::ecs::ClientLocomotion`: `inCombatStance`.
- `keen::three_c::CombatModifierDebugMessage`: `isInCombat` — поле отладки
  камеры, а не подтверждённый авторитетный флаг игрока.
- `keen::ecs::ControlCombatTarget`: `targetId` и `attackSequenceId`.
- `keen::ecs::PlayerCombatTarget`: важность цели; само наличие компонента
  не означает активный бой.

В Enshwick есть [маршрут `set_cluster_combat_state`](https://github.com/enshwick/enshwick/blob/535efb4944f99b84de6c5cd12378042b0485d3dc/crates/enshwick-gamedata/anchors/routes.toml#L3914).
Имя системы не раскрывает её семантику, привязку к игроку или публичный getter.
`enemy01::CombatState` описывает ИИ врагов и не должен подменять состояние игрока.

Проверять кандидаты нужно при спокойном передвижении, доставании оружия,
добыче, агрессии врага до первого попадания, атаке, получении урона и выходе
из боя. Сопоставить времена с игровыми часами, выяснить, кто обновляет поля,
и присутствуют ли они на хосте у каждого гостя. Пока этого нет, не считать
стойку или камеру надёжной проверкой боя. При неизвестном состоянии политика
сохраняет стандартный расход бега и прыжков.

`HitEvent` пригоден для наблюдения попаданий, но сам по себе не определяет
начало/конец боя: до первого попадания уже может идти бой; сбор ресурсов
тоже нельзя автоматически считать боем. Таймер после урона остаётся возможной
эвристикой, а не текущей реализацией.

## Хост, гости и стамина

Enshwick [описывает клиентскую таблицу сборки 26320373](https://github.com/enshwick/enshwick/blob/535efb4944f99b84de6c5cd12378042b0485d3dc/crates/enshwick-gamedata/tables/client-69f0e9573b32c24a8838d3fff550824c-520.toml#L13):
клиент содержит сервер, работающий на потоке `GameServer` при хостинге.
Его документация событий также явно описывает события этого встроенного сервера.

[EMF: combat](https://github.com/matenm/emf-enshrouded/blob/7d014b2d42cb63196fe147a389ed13dea69d1f6d/docs/engine_parts/combat.md)
описывает серверные атрибуты и расход стамины при блокировании удара.
Это НЕ доказательство, что расходы бега, прыжка и добычи идут тем же путём.
В типах также есть `NetworkStamina`, но одно его наличие не доказывает
авторитетность хоста для всех видов расхода.

Нужно установить источник каждого расхода, отличить дерево/руду от врага,
найти предсказание/сверку на клиенте. Только затем проверить модded-хост с
немодифицированным гостем. Стандартная репликация должна доставлять результат
без модового сетевого протокола и без постоянных исправлений запаса. Если
для этого необходим код гостя, поддержать клиентские установки Windows/Proton.

## Следующий этап реализации

1. Получить точный Steam build ID/версию EXE и подтвердить поддержку загрузчиком.
2. Через Enshwick сделать read-only probe: версия, роли мира, ID игроков,
   наличие/значения кандидатов CombatStance и событий; корректно переживать
   загрузку/выход из мира. Не менять стамину.
3. Проверить семантику боя и расходы на одной установке; логировать отдельно
   бег, прыжок, добычу и удар по врагу. Нельзя назначать смысл storage-слотам
   или неподтверждённым адресам по названию компонента.
4. Подключить нашу политику сначала к бегу, затем к остальным действиям.
5. Проверить гостя без модов и совместимость DLL под Proton и Windows.

Ни один из этих игровых экспериментов пока не выполнен. Текущие unit-тесты
проверяют только независимую политику. Чужие инсталляторы и DLL при исследовании
не запускались; в проект не скопирован код исследованных модов.
